# Sentinel's Journal

## 2026-11-09 - Unvalidated Article URL in `markToKeep` Same-Domain Iframe Retention
**Vulnerability:** In `src/utils/dom/mark-to-keep.js`, `markToKeep` accepted `url` and interpolated `protocol` and `hostname` directly into a CSS attribute selector (`iframe[src^="${protocol}//${hostname}"]`) without validating them using `validateUrl`. An unvalidated, malformed, or non-web URL (such as `file:`, `javascript:`, or relative URLs) resulted in invalid selector fragments (e.g. `iframe[src^="null//null"]`) or could inadvertently retain unexpected or unsafe iframe elements that `stripJunkTags` is designed to eliminate.
**Learning:** Even helper utilities that construct dynamic CSS selectors based on URLs must validate that the URL has an approved web protocol (`http:` or `https:`) and hostname before synthesizing selector rules that exempt content from cleanup routines.
**Prevention:** Always validate `url` with `validateUrl(URL.parse(url))` before constructing origin-specific DOM keep selectors, skipping the dynamic selector if the URL is invalid or dangerous.

## 2026-11-08 - Unvalidated Document `<base href>` in Link Absolutization (Protocol Smuggling & Open Redirects)
**Vulnerability:** In `src/utils/dom/make-links-absolute.js`, `absolutize` inspected `$('base').attr('href')` from untrusted documents without verifying whether the URL adhered to a safe HTTP/HTTPS protocol. Attackers could supply `<base href="javascript:alert(1)/">`, `data:`, `file:`, or arbitrary schemes, leading `URL.resolve` to prepend dangerous or untrusted schemes to relative URLs within the article content.
**Learning:** Document `<base>` tags affect resolution across all relative links in an article. When resolving relative URLs to absolute URLs from untrusted HTML, the `<base href>` tag must never be trusted blindly.
**Prevention:** Always validate document-provided `<base href>` tags using `validateUrl(URL.parse(candidateBaseUrl))` before using them as the base URL for `URL.resolve`, falling back safely to the already-validated `rootUrl`.

## 2026-11-07 - Unvalidated Next-Page URL Return (Downstream XSS & Protocol Smuggling)
**Vulnerability:** `GenericNextPageUrlExtractor` selected candidate pagination links from untrusted document markup based purely on scoring heuristics and returned `topPage.href` directly without verifying whether the URL adhered to a safe web protocol. Although `collectAllPages` guards its internal recursion with `validateUrl()`, consumers invoking Mercury with `fetchAllPages: false` or calling `GenericNextPageUrlExtractor` directly received unvalidated schemes (such as `javascript:`, `file:`, `ftp:`, or `data:`) in `result.next_page_url`.
**Learning:** Defensive checks placed solely inside consumer workflows (like internal fetch loops) do not safeguard downstream consumers of the returned metadata. Extractors that identify secondary URLs from untrusted HTML must enforce protocol validation before exposing them in extraction outputs.
**Prevention:** In extractors outputting navigation or link URLs, validate candidate URLs with `validateUrl(URL.parse(...))` to ensure they use valid `http:` or `https:` protocols before returning them.

## 2026-11-06 - Stored XSS via Dangerous Protocol Candidates in `srcset` Attributes
**Vulnerability:** While `cleanAttributes` in `src/utils/dom/clean-attributes.js` inspected single-URI attributes (`href`, `src`, `xlink:href`) for dangerous protocols, `srcset` was included in `WHITELIST_ATTRS` without candidate URI validation. Untrusted HTML containing `<img srcset="javascript:alert(1) 1x">` or mixed candidates with executable/dangerous schemes (such as `data:text/html,...` or `vbscript:`) had those dangerous candidates preserved in the extracted HTML.
**Learning:** Responsive image attributes like `srcset` accept comma-separated lists of URLs and pixel/width descriptors. Validating single URL attributes does not cover multi-URI attributes where malicious payloads can be hidden in individual candidates or alongside valid image URLs.
**Prevention:** In attribute sanitizers, parse `srcset` candidates and filter out dangerous URI protocols (`javascript:`, `vbscript:`, dangerous non-image `data:`) on each candidate URL, keeping only valid image candidates and removing the `srcset` attribute completely if no safe candidates remain.

## 2026-11-05 - Stored XSS via Dangerous Protocol Attributes in Cleaned Content
**Vulnerability:** While `cleanAttributes` in `src/utils/dom/clean-attributes.js` whitelisted attributes such as `href`, `src`, and `xlink:href`, it did not validate or sanitize their URL schemes. Untrusted documents containing `href="javascript:..."`, `href="vbscript:..."`, or arbitrary `data:` URIs (such as `data:text/html,...`) had those attributes preserved directly in the extracted article HTML, enabling stored XSS in reading clients and web applications rendering the parser's output.
**Learning:** Attribute whitelisting is necessary but insufficient when attributes can accept URI values. Attackers can execute arbitrary JavaScript in the context of the consuming application via malicious schemes embedded in permitted attributes like `<a>` hrefs or `<img>` srcs.
**Prevention:** In DOM cleaners and attribute sanitizers, inspect URL attributes (`href`, `src`, `xlink:href`) for executable or dangerous protocols (`javascript:`, `vbscript:`, non-image `data:`) and strip them while preserving safe protocols, relative paths, and legitimate inline image data (`data:image/...`).

## 2026-11-04 - Unvalidated Canonical URL Extraction (Downstream XSS & Scheme Smuggling)
**Vulnerability:** `GenericUrlExtractor` extracted `<link rel="canonical" href="...">` and `<meta property="og:url" content="...">` directly from untrusted HTML documents without validating the scheme or hostname, allowing dangerous URIs like `javascript:`, `file:`, or `data:` to be propagated into the parser's returned `url` property with `domain: null`.
**Learning:** Downstream consumers (reading applications, share extensions, bookmarkers) frequently take the canonical `result.url` output and render it as clickable links or pass it to web views / HTTP clients assuming the parser only yields web URLs. Extractors that scrape URLs from HTML documents must validate URLs before setting them as canonical representations.
**Prevention:** Always validate extracted canonical or metadata URLs using `validateUrl(URL.parse(...))` and fall back to the safe, already-validated entry URL if the extracted candidate is invalid or dangerous.

## 2026-10-31 - Unvalidated Secondary Link Traversal (SSRF via Pagination)
**Vulnerability:** Secondary URLs discovered within parsed HTML documents (specifically `next_page_url` in `collectAllPages`) were fetched recursively via `Resource.create()` without being subject to the URL protocol validation enforced on the initial entry URL in `Parser.parse()`. Attackers could control the page content or custom extractors to emit dangerous schemes (such as `file://`, `ftp://`, or internal URLs) to trigger SSRF or protocol smuggling during pagination.
**Learning:** URL sanitization and validation must not be confined to external entry points; any secondary or discovered URLs extracted from untrusted payloads that are passed to HTTP/resource fetchers must be validated before issuing network or local filesystem requests.
**Prevention:** Always run `validateUrl()` on any parsed URL candidate before passing it to `Resource.create()` in recursive fetch routines like pagination crawlers.
